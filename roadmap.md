# DevOps Diploma — Roadmap

## Текущее состояние

Выбран вариант **self-hosted Kubernetes на Compute Cloud**, а не Managed Kubernetes:

- Terraform находится в `tf/`, state настроен на S3-бэкенд Yandex Object Storage.
- Создаются VPC, 2 public-подсети (`192.168.1.0/24`, `192.168.2.0/24`) и 2 private-подсети (`192.168.10.0/24`, `192.168.20.0/24`) в зонах `ru-central1-a/b`.
- Есть NAT, bastion, admin VM, 3 control-plane VM и 3 worker VM — все роли описаны в `var.vms`.
- Ansible-плейбуки устанавливают containerd и Kubernetes, инициализируют кластер через `kubeadm`, присоединяют ноды и устанавливают Flannel.
- Управление кластером идёт с `admin`-ноды: там стоит `kubectl` и лежит `~/.kube/config`. На master-нодах копий kubeconfig нет — только рабочий `/etc/kubernetes/admin.conf` для самого `kubeadm`. Локальный `~/.kube/config` рабочей машины устарел (указывает на `192.168.10.23` и недоступен) — работать нужно с `admin`-ноды.
- Terraform генерирует `ansible.cfg` и inventory из `tf/templates/` после создания VM.
- Container Registry описан в Terraform (`tf/40-docker-registry.tf`): реестр `crpj27virc0v36d3u7rq` (имя `main`), репозиторий `crpj27virc0v36d3u7rq/hub`. Ранее собранный образ лежал в другом реестре (`crpm7r21f2egucb6leru`), которого больше не существует, — образ будет пересобран пайплайном.
- Тестовое приложение живёт в отдельном git-репозитории `web-app/` (вложен в этот каталог) и опубликовано на GitHub (`Arthur-Politiko/web-app`). Его манифесты — внутри него, в `k8s/`.
- Манифесты Kubernetes, мониторинг, ingress, деплой приложения и CI/CD развёрнуты. Состояние по каждому — в разделах 5–7.

## 2. Self-hosted Kubernetes через Ansible

### Структура плейбуков

Номер файла совпадает с шагом выполнения. Блоки нумерации: `0x` — подготовка инфраструктуры и узлов, кластера ещё нет; `1x` — подготовка узлов Kubernetes; `2x` — сборка кластера; `3x` — дополнения в уже собранном кластере.

```
01-bootstrap.yaml            установка Python на узлы
02-nat-gateway.yaml          NAT-нода: masquerade для выхода private-нод в интернет
03-admin-prepare.yaml        apt-репозиторий Kubernetes и kubectl на admin
10-k8s-common.yaml           подготовка узлов и установка Kubernetes
11-master.yaml               настройка master-нод
20-kubeadm-init.yaml         kubeadm init
21-kubeadm-join.yaml         присоединение workers
22-kubeadm-join-master.yaml  присоединение дополнительных master
23-admin-kube-config.yaml    kubeconfig на admin и проверка доступа
24-flannel.yaml              Flannel CNI и ожидание готовности всех нод
30-monitoring.yaml           стек мониторинга kube-prometheus-stack через helm
31-ingress.yaml              ingress-nginx и публикация Grafana на 80 порту
32-ci.yaml                   TeamCity на admin-ноде: сервер, агент, UI на 80 порту
33-app-prepare.yaml          namespace приложения, права пайплайна, манифесты
```

`02-nat-gateway.yaml` идёт первым шагом цепочки: без masquerade у private-нод нет интернета, и всё, что что-то скачивает (apt, `pkgs.k8s.io`, `download.docker.com`, `get.helm.sh`, `git clone`), падает. Сам он работает через `raw`, поэтому Python на нодах ему не нужен.

`03-admin-prepare.yaml` от кластера не зависит и может запускаться отдельно, чтобы прогреть admin-ноду заранее. `30-monitoring.yaml` и `31-ingress.yaml` тоже запускаются отдельно: они ставятся в уже готовый кластер и подключены последними шагами в `90-install-k8s.yaml`.

**Запускать плейбуки нужно из каталога `ansible/`.** Там лежит `ansible.cfg`, который Ansible подхватывает только из текущего каталога: в нём ProxyCommand через bastion и относительные пути (`inventory = inventory.ini`, ключ `../vault/id_ed25519`). При запуске из корня репозитория конфиг не применяется, и Ansible идёт к нодам напрямую по приватным адресам, упираясь в таймаут.

```bash
cd ansible && ansible-playbook -i inventory.ini 90-install-k8s.yaml
```

## 5. Мониторинг

Задача этапа по README диплома: задеплоить Prometheus, Grafana, Alertmanager и экспортер метрик Kubernetes, отдать веб-интерфейс Grafana на 80 порту и показать дашборды состояния кластера. Рекомендованный способ — пакет `kube-prometheus-stack` (Kubernetes-оператор, включает всё перечисленное), альтернатива — набор helm-чартов Bitnami.

### Что за компоненты и как они связаны

| Компонент | Роль |
|---|---|
| `node_exporter` | Агент на каждой ноде, отдаёт метрики хоста на `:9100/metrics`: CPU, память, диски, сеть, load average. В чарте ставится DaemonSet'ом — по поду на ноду. |
| Prometheus | Сам опрашивает (scrape) экспортеры по расписанию, хранит метрики в своей TSDB и считает правила на языке PromQL. |
| Alertmanager | Принимает уже сработавшие алерты от Prometheus, группирует и дедуплицирует их, умеет глушить (silence) и рассылает получателям: Telegram, e-mail, Slack, webhook. Правила сам не считает. |
| Grafana | Визуализация: читает Prometheus как datasource и рисует дашборды. Метрики не хранит. |
| kube-state-metrics | Входит в чарт. Метрики объектов Kubernetes — состояние deployment, подов, число реплик. В отличие от `node_exporter`, который про железо. |

Поток данных: экспортеры → scrape → Prometheus → сработавшие алерты → Alertmanager → получатель. Grafana отдельно ходит запросами в Prometheus.

### Решение по размещению

Разворачиваем **внутри кластера** через `kube-prometheus-stack`, а не на отдельной VM:

- так рекомендует сам диплом, и дашборды состояния кластера работают «из коробки»;
- `node_exporter` в виде DaemonSet автоматически покрывает все ноды, включая добавленные позже;
- метрики control plane (kubelet/cAdvisor, apiserver, kube-state-metrics) подключаются ServiceMonitor'ами, без ручного scrape-конфига с TLS и аутентификацией;
- стек укладывается примерно в 1–1.5 ГБ RAM, а отдельная VM — это ещё одна прерываемая машина в бюджете купона.

Идея «отдельной ноды» реализуется внутри кластера: закрепить мониторинг на конкретном worker через `nodeSelector` (при желании — с taint), чтобы прикладные поды не вытесняли Prometheus.

Отдельная VM имеет смысл только в одном сценарии — если мониторинг должен переживать падение кластера. Для диплома это не требуется, но если выбирать этот путь, `node_exporter` придётся ставить на все VM через Ansible, а метрики Kubernetes собирать вручную.

### Вариант установки

Оба варианта ставят один и тот же стек: helm-чарт `kube-prometheus-stack` генерируется из этого же проекта, различается только обвязка.

- **`kube-prometheus` (манифесты)** — проще в текущем стенде: `kubectl` уже есть на `admin`-ноде, а `helm` установлен только на рабочей машине, откуда API-сервер недоступен. Скомпилированные манифесты лежат в репозитории, jsonnet для установки не нужен:

  ```bash

  cd kube-prometheus
  kubectl apply --server-side -f manifests/setup
  kubectl wait --for condition=Established --all CustomResourceDefinition --namespace=monitoring
  kubectl apply -f manifests/
  ```

  Ветка `release-0.19` — по таблице совместимости она поддерживает Kubernetes 1.35, который стоит в кластере.

## 6. Terraform CI/CD

Требование этапа: изменения инфраструктуры идут через пайплайн — план до применения, apply под контролем, пример PR или скриншоты для сдачи. Задание допускает три варианта: Terraform Cloud, Atlantis или пайплайн в своей CI-системе.

### Выбор: пайплайн в существующем TeamCity

- **Почему не Atlantis** (рекомендованный в задании): он разворачивается в кластере, а для хранения планов ему нужен постоянный том. StorageClass в кластере нет — проверено 2026-09-30, `kubectl get storageclass` пуст (мониторинг по этой же причине живёт на `emptyDir`). Плюс ему нужны вебхук из GitHub, токен и отдельный набор креденшелов внутри пода.
- **Почему не Terraform Cloud**: это перенос state в чужую систему, хотя S3-бэкенд с версионированием уже работает и проверен. Плюс `tf/` через провайдер `local` пишет `ansible.cfg` и `inventory.ini` на диск оператора — при удалённом прогоне файлы создались бы на раннере Terraform Cloud и до нас бы не доехали.
- **Почему TeamCity**: развёрнут, интерфейс доступен по HTTP (требование диплома), агент с Docker и kubectl уже есть, креденшелы и грабли известны. Задание прямо разрешает этот путь: «вместо Terraform Cloud или atlantis настройте автоматический запуск и применение конфигурации terraform из вашего git-репозитория в выбранной вами CI-CD системе».

Плата та же, что и у приложения: конфигурация сборок создаётся руками и живёт в базе сервера — см. пункт в разделе 7.

### Две сборки

| Сборка | Триггер | Что делает |
|---|---|---|
| `Terraform_Plan` | VCS, фильтр `+:main` | `fmt -check`, `validate`, `init`, `plan -out=tfplan`; публикует `plan.txt` артефактом |
| `Terraform_Apply` | без VCS-триггера, запуск руками | `init`, `apply tfplan` из последней успешной `Terraform_Plan` той же ревизии |

Контроль apply держит человек: план лежит артефактом в сборке, apply запускается кнопкой — это и есть «controlled apply после review» из задания. Связка сборок — snapshot- и артефактная зависимость, чтобы применялся план именно той ревизии.

**Что реализовано на самом деле (проверено 2026-10-06):** скрипт `ci/teamcity-setup.sh` создаёт **одну** сборку `Terraform_Apply` с VCS-триггером `+:main`. В одном шаге идут `fmt -check`, `init`, `validate` и `plan -out=tfplan`, а `apply -auto-approve tfplan` добавляется только при запуске скрипта с `APPLY=1`. Артефактами публикуются `ansible/ansible.cfg` и `ansible/inventory.ini` (`plan.txt` не публикуется). Отсюда следствие, которое стоит знать до включения применения: с `APPLY=1` apply будет проходить автоматически на каждый коммит в `main`, без ручного подтверждения, — контроль держится не кнопкой, а флагом в момент создания сборки. Если нужна схема «план на коммит, применение руками» из таблицы выше, это две отдельные сборки, и скрипт их пока не создаёт.

Опционально, если нужен именно PR: добавить в `branchSpec` правило `+:refs/pull/*/head` и включить в TeamCity поддержку pull request'ов — тогда план запускается на PR и отмечается статусом в GitHub. Для сдачи достаточно скриншотов пайплайна.

## 7. Application CI/CD

### Архитектура

TeamCity работает **на admin-ноде, а не в кластере**. Причины:

- сборка идёт хостовым Docker: не нужны docker-in-docker, privileged-поды и StorageClass, которого в кластере нет;
- данные сервера (история, настройки, пользователи, лицензия) лежат на диске ноды в `/home/ubuntu/teamcity` и переживают перезапуск контейнера — в кластере это был `emptyDir`, терявшийся при переезде пода;
- `kubectl` и рабочий kubeconfig уже есть на ноде, пайплайну остаётся смонтировать их в контейнер агента.

Разделение ответственности:

| Кто | Чем владеет |
| --- | --- |
| Terraform | инфраструктура: VM, сеть, реестр, статический IP, DNS |
| Ansible | форма приложения в кластере: Namespace, Deployment, Service, Ingress и права пайплайна |
| TeamCity | версия образа: собрать, запушить, обновить тег у Deployment, дождаться прокатки |

Разделение закреплено в `ansible/33-app-prepare.yaml`: манифесты приложения Ansible забирает `git clone` из репозитория `web-app` (публичного, креды не нужны) и применяет их, а пайплайну остаётся `kubectl set image` и `rollout status`. Так применённое состояние привязано к ревизии репозитория, а не к рабочему дереву на машине оператора.

Схема потока:

```
git push (main)  → VCS-триггер TeamCity → сборка образа (агент, хостовый Docker)
                                        → push в cr.yandex с тегом номера сборки и latest
git push (тег)   → VCS-триггер WebApp_release → сборка с тегом версии
                                             → push в cr.yandex
                                             → kubectl set image + rollout status (SA ci-deployer)
```

- [x] **Пуш образа в cr.yandex с современным Docker.** `docker build` + `docker push` падают с `Cannot read manifest data`: Docker 29 собирает OCI-манифест с аттестациями (provenance/sbom), а реестр Yandex Cloud принимает только классический Docker v2 schema 2. - [x] **Многострочный скрипт в шаге сборки через REST API.** В XML-атрибуте перевод строки нормализуется в пробел, поэтому скрипт передаётся с `&#10;` вместо реальных переводов строк (или пишется отдельным plain-text запросом). Иначе шаг получает одну длинную строку мусора. Тот же приём нужен для `teamcity:branchSpec`: без него список правил (ветки + теги) склеивается в одну строку, второе правило не распознаётся, и теги не попадают в спецификацию.
- [x] **VCS root молча не привязывается к сборке.** `POST /app/rest/buildTypes/id:<id>/vcs-root-entries` с телом `<vcs-root-entry><vcs-root id="..."/></vcs-root-entry>` возвращает `200`, но запись не создаётся — обязательно нужен вложенный `<checkout-rules/>`. Симптом: в сборке пустой `vcs-root-entries`, TeamCity вообще не проверяет репозиторий (зеркала git на диске нет), не работает ни один триггер.

- [x] **Тег на том же коммите, что и вершина `main`.** TeamCity определяет ветку сборки по ревизии и отдаёт сборку на `main`, даже если запустил её тег: у нас `v1.0.0` и `v1.1.0` указывают на тот же коммит, что и `main`. Поэтому версия определяется в скрипте в три попытки — имя ветки TeamCity, затем `git tag --points-at HEAD`, затем `git ls-remote --tags` по SHA коммита; из подходящих тегов берётся старший (`sort -V | tail -1`). Если тега на ревизии нет, сборка сообщает «релизить нечего» и завершается успешно.
- [x] **REST API принимает JSON, но падает на XML.** 2026-09-30: `POST /app/rest/projects` с XML-телом отвечает `HTTP 500`, а в `teamcity-rest.log` лежит `IllegalArgumentException: argument type mismatch`; клиенту при этом отдаётся HTML-страница с заголовком «TeamCity Maintenance», из-за чего легко решить, что сервер ушёл в режим обслуживания. - [x] **CSRF-защита TeamCity.** POST-запросы к API требуют токен: сначала `GET /` (создаёт сессию), затем `GET /authenticationTest.html?csrf`, затем заголовок `X-TC-CSRF-Token` в том же сеансе. JetBrains для автоматизации рекомендует Bearer-токен — тогда проверка не применяется вовсе.
- [x] **`kubectl` в контейнере агента.** Если смонтировать несуществующий путь, Docker создаст на его месте каталог, и внутри контейнера `kubectl` окажется директорией. Путь узнаётся на месте: `command -v kubectl` (пакет ставит его в `/usr/bin`, а не в `/usr/local/bin`).
- [x] **Долгоживущий токен ServiceAccount.** Штатный токен живёт час, для внешнего kubeconfig он не годится — нужен Secret типа `kubernetes.io/service-account-token`. У `kubectl config set-cluster` нет флага `--certificate-authority-data`: CA передаётся файлом с `--embed-certs=true`, иначе сертификат в kubeconfig не попадёт и `kubectl` уйдёт на `localhost:8080`.
- [x] **Проба готовности.** Первый старт сервера — режим обслуживания, обычные страницы отдают 503, пока администратор не подтвердит запуск в браузере. Рабочая проба — `/healthCheck/healthy`: отвечает 200 и во время инициализации. `liveness`-проба вредна: во время долгой инициализации она убивает контейнер и запуск начинается заново.

## 9. Миграция CI/CD на Jenkins

Причина: у TeamCity конфигурация сборок живёт в базе сервера и создаётся REST-скриптом, то есть пересборку стенда она не переживает (раздел 7). У Jenkins конфигурация описывается целиком из Ansible (JCasC), а логика сборок — `Jenkinsfile` в репозитории.

Целевое разделение:

| Слой | Кто владеет | Переживает пересборку |
|---|---|---|
| Контейнер, плагины, пользователь, описания job'ов | Ansible + `k8s/ci/jenkins-casc.yaml.j2` | да |
| Логика сборки и деплоя | `Jenkinsfile` в репозитории | да |
| Данные Jenkins (история) | диск admin-ноды | нет, и не нужны |
